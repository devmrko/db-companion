# DB Companion 첫 사용 가이드

[English](GETTING-STARTED.md) · [简体中文](GETTING-STARTED.zh-CN.md) · [日本語](GETTING-STARTED.ja.md) · [화면 가이드](SCREEN-GUIDE.md)

로그인 → 준비 상태 확인 → 메타데이터 조회 → SQL 생성·검토·실행 순서로 진행합니다. Wallet이나 계정이 없다면 [시작 전 준비물과 관리자 요청 양식](../README.md#before-you-start)을 확인하세요. 변경 이력 설치는 첫 조회의 필수 조건이 아닙니다.

## 1. 접속 대상 확인

올바른 Wallet과 TNS 서비스를 고르고 실제 Oracle 계정으로 로그인합니다. **접속 정보**에서 DB, 로그인 사용자, 선택한 스키마를 확인한 뒤 변경 작업을 시작하세요. 스키마 선택은 탐색 범위만 바꾸며 로그인 계정이나 권한을 바꾸지 않습니다. 관리자에게 설정을 요청할 때는 같은 DB/Wallet과 대상 스키마·객체를 알려 주세요. 비밀번호는 공유하지 마세요.

## 2. 준비 상태 확인

빈 전용 스키마로 실습한다면 먼저 **시작 → 실습 데이터 준비**(`/db/demo-data`)에서 업무 상황·질문·규칙·기준일·행 수를 입력해 프롬프트를 받습니다. Codex에 전달해 DDL·가상 데이터·검증 SQL·업무 규칙 파일을 검토하고, 실제 접속 DB와 소유자를 확인한 뒤 SQLcl로 실행합니다. SQL 파일은 UTF-8로 저장하고 SQLcl에서 `SET ENCODING UTF-8` 후 읽습니다. 이 화면은 프롬프트만 만들며 AI 호출이나 DB 변경을 하지 않습니다. 데이터 생성 뒤 같은 객체에 아래 설정을 이어갑니다.

대시보드에서 항목별 **완료 / 부족 / 확인 불가**를 확인하고 **준비 상태 상세**로 이동합니다. 요약은 첫 활성 프로필을 우선 사용하므로 상세 화면에서 실제 사용할 프로필을 선택하세요. 완료는 설정 조회 결과이며 실행 성공을 뜻하지 않습니다. 부족은 설정 화면에서 조치하고, 확인 불가는 조회 권한·연결·지원 여부를 확인합니다. [준비 상태 안내](setup-readiness.md)에서 확인 범위를 볼 수 있습니다.

## 3. 첫 메타데이터 조회

**테이블·뷰·컬럼**에서 허용된 스키마와 객체를 선택하고 컬럼·제약조건을 확인합니다. 기대한 객체와 컬럼이 보이면 메타데이터 조회를 확인한 것입니다. 빈 목록이나 접근 오류는 대상 스키마와 권한을 확인하세요. 코멘트 수정이나 이력 설치는 필요하지 않습니다. AI 준비가 부족해도 접근 가능한 메타데이터는 조회할 수 있습니다.

## 4. SQL 생성·검토·실행

준비 상태에서 확인한 프로필을 **Select AI 테스트**에서 선택하고 질문을 입력합니다. 전송할 질문·문맥과 비용을 확인한 뒤 SQL을 생성합니다. 프로필 대상 객체, 프롬프트·참고정보, 생성 SQL을 검토하고 허용된 조회만 명시적으로 실행합니다. 결과는 신뢰할 수 있는 업무 기준과 대조하세요. AI 검토나 SQL 실행 성공만으로 업무 정답이 확인되지는 않습니다. AI로 업무 데이터를 변경하는 것은 입문 절차가 아닙니다. [화면 가이드](SCREEN-GUIDE.md)와 화면의 **SQL ?**를 참고하세요.

Semantic Release 저장소가 준비됐으나 운영 배포 버전이 없다면 실행이 차단될 수 있습니다. 개발 실습은 **시멘틱 배포 → 개발 모드(현재 설정)**를 명시적으로 선택하거나 검토한 첫 버전을 배포합니다. 개발 모드 선택을 운영 배포 보호의 전역 해제로 대체하지 않습니다.

## 선택 기능

이력·수집 기능은 필요한 경우에만 담당자에게 별도로 요청합니다. `ADMIN`은 가능한 계정 중 하나이지 모든 기능의 고정 필수 계정이 아닙니다.

### 역할과 순서

| 담당 | 먼저 할 일 |
| --- | --- |
| 일반 사용자 | 접속을 확인하고 접근 가능한 객체·정의를 탐색하며 준비된 Select AI 프로필을 사용합니다. 이력 설정이 비활성화되거나 설치가 빠졌으면 설정을 요청합니다. |
| 기록된 트리거 소유자 또는 필요한 권한을 가진 설치자 | 대상 테이블/뷰별 메타데이터 이력 코드를 확인·설치·업데이트하고 수집을 켠 다음 객체별 이력 접근을 설정합니다. 기존 설치는 기록된 트리거 소유 계정을 사용합니다. |
| 앱 저장소·기타 수집 기능의 소유자 | 기능별 저장소, 직접 부여된 권한, 수집 Job을 필요에 따라 준비합니다. 프로필은 소유자가 관리하고 SQL 캐시·DDS 보관소는 각 수집 설정의 소유 계정에 둡니다. 모든 저장소를 `ADMIN`이 만드는 것은 아닙니다. |

설치와 권한 부여는 DB를 변경하며 별도로 커밋될 수 있습니다. 담당자는 UI 미리보기와 현재 권한을 검토한 뒤 적용하세요.

### 기능별 ADMIN 사전 조치

ADB에서 새 일반 계정을 준비할 때는 **계정 생성·권한 설정**과 각 기능의 권한 안내를 사용합니다. 현재 계정·같은 DB·대상 스키마를 확인하고 필요한 기능만 적용합니다.

| 사용할 기능 | 관리자 작업 | 일반 계정에서 확인 |
| --- | --- | --- |
| Native Semantic Source | AI 프로필의 Semantic Source 권한 화면에서 조회된 DBMS_AI_SEM 패키지의 EXECUTE를 미리보기 후 부여 | Source 조회·생성, 프로필 semantic_source 연결, 실제 SQL 생성까지 확인 |
| 업무 용어 검색 | Oracle Text가 필요하면 TEXT 권한 안내의 CTXSYS.CTX_DDL 실행 권한 부여 | 용어 테이블·이력·Text 인덱스 준비 후 검색과 변경 이력 확인 |
| SQL 캐시 보관 | SQL_CACHE 안내의 SYS.V_$SQL 조회 권한 확인; 수집 소유자에게 CREATE TABLE/JOB와 quota 준비 | 수집 설치, 최근 Job 성공, 후보 목록·상세 확인 |
| DDS Data Grant 관리 | DDS 권한과 DDS · 자기 스키마 Data Grant 관리 권한을 각각 미리보기 후 부여 | 자기 스키마의 정책 생성·재조회. 사용자 A/B의 실제 접근은 별도로 검증 |
| 프로필 계정 감사 | 권한 있는 감사 관리자가 대상 계정의 감사를 명시적으로 활성화하고 수집 | 앱 경유 변경 전후 이력과 원본 감사 호출을 구분; 분류 불가 호출은 변경으로 추정하지 않음 |

Resource Principal을 사용할 때는 ADB ADMIN이 해당 실습 계정에 `DBMS_CLOUD_ADMIN.ENABLE_RESOURCE_PRINCIPAL`을 실행하고, OCI 관리자가 해당 ADB의 모델 호출 정책·리전·구획을 준비합니다. Credential 목록에 이름이 보이는 것만으로 OCI 권한과 모델 호출이 검증되지는 않습니다. API Key 본문을 앱이나 문서에 붙이지 않습니다.

전역 CUSTOM 용어 콜백은 전역 응답 계약을 따라야 합니다. DB Companion 생성 함수는 `term`/`definition`을 반환합니다. 전역 응답에 `applies_to`를 넣은 구버전은 Source 생성이 성공해도 실제 SQL 생성에서 거절될 수 있으므로 **업무 용어 검색 함수**에서 상태·업데이트 SQL을 확인합니다. **설정 변경 이력**은 Source의 설정 전후 값과 생성 콜백의 설치 버전·해시·결과를 기록합니다. 프로필 연결·업무 용어 이력과 구별하며, 함수 원문은 Git에서 관리합니다. [설정 변경과 설치 기록](semantic-source-history.md)을 참고하세요.

### 메타데이터 변경 이력 준비

이 기능은 테이블/뷰/컬럼 코멘트와 지원되는 Annotation의 변경을 기록합니다. 업무 데이터 행의 변경 이력은 아닙니다. 권한 있는 담당자는 다음 순서로 진행합니다.

1. 기존 대상은 기록된 트리거 소유자로, 새 대상은 적절한 설치 권한 계정으로 **같은 DB**에 로그인합니다. **테이블·뷰·컬럼**에서 대상 스키마를 선택합니다. 관리자 스키마를 선택하는 것만으로 권한이 생기지 않습니다.
2. 대상 테이블/뷰를 엽니다. 여러 대상은 **이력 일괄·권한 설정**에서 프로필의 `object_list`를 선택해 미리봅니다. 프로필은 대상 묶음이지 별도 이력 저장소가 아닙니다. 확인된 객체를 검토하고 다른 스키마는 스키마별로 처리합니다.
3. **설치 확인**에서 공통 패키지와 대상 트리거의 유효성, 상태, 다음 작업, 설치 권한을 확인합니다. 알려진 구버전 코드는 표시된 순서로 업데이트하고 트리거가 없으면 **트리거 설치·켜기**를 사용합니다. 알 수 없거나 호환되지 않는 코드는 수동 검토가 필요합니다. 코드가 **Ready**여도 수집이 켜졌다는 뜻은 아닙니다.
4. 준비된 대상에서 **이력 관리**를 켭니다. **이력 일괄·권한 설정**에서 특정 기존 DB 사용자에게 **조회 허용** 또는 **조회·수집 ON/OFF 허용**을 대상별로 설정합니다. 후자는 검증된 기존 수집기의 ON/OFF만 바꾸며 코드 설치·교체는 못 합니다. 범위를 확인해 적용하고 **전체 사용자 (PUBLIC)**를 기본값으로 선택하지 마세요.
5. 일반 사용자는 재접속하거나 새로고침한 뒤 대상의 **변경 이력**과 상태를 확인합니다. 수집은 메타데이터를 실제 변경한 DB 사용자를 기록합니다. 사용자별 설정은 누가 조회하거나 ON/OFF를 관리하는지만 정하며 기록할 변경자를 걸러내지 않습니다. 같은 객체의 설정은 프로필 간에 공유됩니다.

설치자 소유권, 부분 적용, 위임 범위는 [메타데이터 이력 접근](metadata-history-access.md)과 [코드 업데이트](metadata-history-upgrades.md)를 참고하세요.

### 서로 다른 이력 구분

| 출처 | 확인할 점 |
| --- | --- |
| 메타데이터 변경 이력 | 설치·활성화된 트리거가 지원되는 코멘트/Annotation 변경을 기록합니다. 미설치와 활성화 후 변경이 없는 상태는 다릅니다. |
| 앱 저장 이력 | 명시적으로 저장한 실행/문제 질문 자료와 지원되는 설정 변경은 각 저장소와 범위를 가집니다. 세션 상태는 DB 영속 기록이 아니며 외부 변경이 소급 기록되지는 않을 수 있습니다. |
| Native 질문·Agent 이력 | 대화 ID와 보관 설정을 사용한 질문·응답, Team/Task 실행의 입력·결과를 각 원본 뷰에서 조회합니다. RUN_TEAM은 준비된 conversation_id를 params에 전달합니다. 일반 SQL 조회 결과 셀 전체가 자동 보관된다는 뜻은 아닙니다. |
| SQL 캐시 보관 | 로그인 소유자가 테이블과 Oracle Scheduler Job을 명시적으로 등록해 일부 Select AI 호출 후보를 수집합니다. `V$SQL`에서 사라진 SQL은 놓칠 수 있고 커서 통계는 전수 실행 감사가 아닙니다. 자동 삭제도 보장하지 않습니다. [SQL 캐시 보관](sql-cache-archive.md)을 보세요. |
| Oracle 감사 / DDS 보관 | 원본 감사와 선택적 DDS 보관은 범위와 설정이 다릅니다. 보관은 원본 감사 정책을 자동 설정하거나 만료된 기록을 복구하지 않습니다. DB Scheduler Job은 앱 로그아웃 후에도 실행됩니다. |

보존 기간은 출처와 설정에 따라 달라집니다. 빈 화면만으로 보편적인 보존 일수를 추정하지 마세요.

별도 패키지 호출은 [Callable AI](callable-ai.md)를 참고하세요.

## 빠른 문제 해결

| 증상 | 확인 |
| --- | --- |
| 버튼 비활성화 / 관리자 설정 필요 | **설정 안내**와 **설치 확인**을 열고 기록된 설치자에게 권한과 대상 상태 확인을 요청합니다. |
| **MISSING** | 대상 객체와 패키지·트리거를 확인합니다. 설치는 별도 권한 작업입니다. |
| **READY**인데 이력이 없음 | **이력 관리** ON, 로그인 계정의 조회 권한, 수집 시작 후 지원되는 변경이 있었는지 확인합니다. |
| `ORA-00942` / 접근 검사 | 객체·뷰가 없거나 미지원 또는 접근 불가일 수 있습니다. 관리자가 직접 권한과 원래 ORA 코드를 확인해야 합니다. |
| 예상과 다른 기록·버튼 | Wallet, TNS, DB, 실제 로그인 사용자, 대상 스키마를 다시 확인합니다. 스키마 선택은 로그인을 바꾸지 않습니다. |
