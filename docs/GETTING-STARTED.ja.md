# DB Companion はじめての利用

[English](GETTING-STARTED.md) · [한국어](GETTING-STARTED.ko.md) · [简体中文](GETTING-STARTED.zh-CN.md) · [画面ガイド](SCREEN-GUIDE.md)

一部の履歴・収集機能は、一般ユーザーが記録を見る前に、必要な管理権限を持つDBアカウントによる準備が必要です。対象の所有者と既存トリガーの設置者を確認してください。`ADMIN`は使えるアカウントの一例であり、すべての機能に必須の固定アカウントではありません。

## 1. 接続先を確認

正しいWalletとTNSサービスを選び、実際のOracleアカウントでログインします。**接続情報**でDB、認証されたユーザー、選択中のスキーマを確認してから変更作業を始めます。スキーマ選択は参照範囲を変えるだけで、ログインや権限は変えません。管理者に依頼するときは、同じDB/Walletと対象スキーマ・オブジェクトを伝えます。パスワードは共有しないでください。

## 2. 担当と順序

| 担当 | 最初に行うこと |
| --- | --- |
| 一般ユーザー | 接続を確認し、参照可能な対象と定義を調べ、準備済みのSelect AIプロファイルを使います。履歴操作が無効、または未設置なら設定を依頼します。 |
| 記録済みのトリガー所有者、または適切な権限を持つ設置者 | 対象の表・ビューごとにメタデータ履歴コードを点検・設置・更新し、収集を有効にしてから対象別の履歴アクセスを設定します。既存の設置では記録済みのトリガー所有者を使います。 |
| アプリ保存先や他の収集機能の所有者 | 機能ごとの保存先、直接付与された権限、収集Jobを必要に応じて準備します。プロファイルはその所有者が管理し、SQLキャッシュ・DDSの保存先は各収集設定の所有者が管理します。すべてを`ADMIN`が作るわけではありません。 |

設置と権限付与はDBを変更し、別々にコミットされる場合があります。担当者は画面のプレビューと現在の権限を確認してから適用します。

## 3. 必要に応じてメタデータ変更履歴を設定

対象は表・ビュー・列のコメントと対応するAnnotationの変更です。業務データ行の変更履歴ではありません。権限のある担当者は次の順序で進めます。

1. 既存の対象には記録済みのトリガー所有者で、新規対象には適切な設置権限を持つアカウントで**同じDB**にログインします。**表・ビュー・列**で対象スキーマを選びます。管理者スキーマを選ぶだけでは権限は増えません。
2. 対象の表・ビューを開きます。複数対象は**履歴の一括・権限設定**でプロファイルの`object_list`を選んでプレビューします。プロファイルは対象の集合であり、独立した履歴保存先ではありません。解決された各対象を確認し、異なるスキーマは別々に扱います。
3. **設置を確認**で共通パッケージと対象トリガーの有効性、状態、次の操作、設置権限を調べます。既知の旧コードは表示された手順で更新し、トリガーがない場合は**トリガーを設置・有効化**を使います。不明・非互換のコードは手動確認が必要です。コードが**Ready**でも収集がオンとは限りません。
4. 準備できた対象の**履歴管理**をオンにします。**履歴の一括・権限設定**で実在する特定のDBユーザーに、対象ごとに**履歴の参照を許可**または**参照・収集の切替を許可**を設定します。後者は検証済みの既存収集器のオン・オフだけが可能で、コードの設置・置換はできません。範囲を確認して適用し、**全ユーザー（PUBLIC）**を既定で選ばないでください。
5. 一般ユーザーが再ログインまたは更新して、対象の**変更履歴**と状態を確認します。収集はメタデータを実際に変更したDBユーザーを記録します。ユーザー別設定は参照やオン・オフ管理の可否を決め、記録する変更者を絞りません。同じ対象の設定は複数プロファイルで共有されます。

設置者の所有権、部分適用、委任の範囲は[メタデータ履歴アクセス](metadata-history-access.md)と[コード更新](metadata-history-upgrades.md)を参照してください。

## 4. 履歴の種類を区別

| 出所 | 確認点 |
| --- | --- |
| メタデータ変更履歴 | 設置・有効化されたトリガーが対応するコメント/Annotationの変更を記録します。未設置と、有効化後に変更がない状態は異なります。 |
| アプリが保存する履歴 | 明示的に保存した実行・問題質問の情報と対応する設定変更には、それぞれ保存先と範囲があります。セッション状態はDBの永続記録ではなく、外部変更が遡及して記録されるとは限りません。 |
| SQLキャッシュ保存 | ログイン所有者が表とOracle Scheduler Jobを明示的に登録し、一部のSelect AI呼び出し候補を収集します。`V$SQL`から消えたSQLは見逃す場合があり、カーソル統計は完全な実行監査ではありません。自動削除も保証しません。[SQLキャッシュ保存](sql-cache-archive.md)を参照してください。 |
| Oracle監査 / DDS保存 | 元の監査記録と任意のDDS保存記録は範囲・設定が異なります。保存は元の監査を自動設定せず、期限切れ記録も復元しません。DB Scheduler Jobはアプリのログアウト後も動きます。 |

保持期間は出所と設定次第です。空の画面から一律の保持日数を推測しないでください。

## 5. 最初の有用な照会

接続を確認し、利用可能なプロファイルを選び、関連する業務用語と定義を確認します。**Select AIテスト**でSQLを生成し、プロファイルの対象、プロンプト・根拠、生成SQLを点検してから明示的に照会を実行します。結果は信頼できる業務上の答えと照合してください。AIレビューは説明であり数値検証ではありません。生成・レビューは質問、SQL、選択した文脈を設定済みプロバイダーへ送信し、費用がかかる場合があります。依頼前に送信内容と費用の範囲を確認します。AIによる業務データ変更は初期手順に含めません。[画面ガイド](SCREEN-GUIDE.md)、画面内の**SQL ?**、別のパッケージ手順である[Callable AI](callable-ai.md)を参照してください。

## 簡単なトラブル確認

| 状況 | 確認 |
| --- | --- |
| 操作が無効 / 管理者設定が必要 | **設定手順**と**設置を確認**を開き、記録済みの設置者に権限と対象状態の確認を依頼します。 |
| **MISSING** | 対象とパッケージ・トリガーを確認します。設置には別途権限が必要です。 |
| **READY**だが履歴なし | **履歴管理**がオンか、ログインユーザーの参照権限、収集開始後の対応する変更の有無を確認します。 |
| `ORA-00942` / アクセス確認 | 対象・ビューが存在しない、非対応、または参照不可の可能性があります。管理者に直接権限と元のORAコードの確認を依頼します。 |
| 予想外の記録・操作 | Wallet、TNS、DB、実際のログインユーザー、対象スキーマを再確認します。スキーマ選択でログインは変わりません。 |
