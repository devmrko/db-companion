# Semantic Source 설정 변경과 설치 기록

질문에 연결된 Source가 바뀌었을 때 무엇을 변경했는지 확인하는 기능입니다. AI 프로필의 **Semantic Context**에서 Source 설정을 선택하고, 변경 전후 값과 사용자·시각·확인 결과를 조회합니다. 생성 콜백은 Git의 코드 버전과 연결할 수 있도록 설치 버전·소스 해시·결과만 기록합니다.

## 처음 준비하기

1. 소유 계정으로 로그인하고 같은 스키마를 선택합니다. Native Source 사용에는 지원 버전·DBMS_AI_SEM 실행 권한이 필요합니다. 필요한 권한은 [첫 사용 가이드](GETTING-STARTED.ko.md#기능별-admin-사전-조치)에서 확인합니다.
2. **Semantic Context → 설정 변경 이력**에서 기록 저장소 상태를 확인합니다. 기존 `DBC_APP_RECORD`를 재사용하며, 없으면 표시된 설치 SQL을 검토하고 동의해 준비합니다. 새 테이블을 만들 때는 소유자의 CREATE TABLE과 quota가 필요합니다. 다른 사용자의 기록을 조회하는 광범위한 권한은 부여하지 않습니다.
3. Source를 생성하면 실제 생성 전의 부재 상태와 요청, DB에서 읽은 생성 후 설정이 기록됩니다. 준비된 기록 저장소가 없으면 native 변경 전에 중단합니다.

## 설정 수정

1. Source 행의 **Source 설정 변경**을 엽니다.
2. 지원 작업은 활성화·비활성화, CUSTOM global Source의 `global_callback_func`·`params` 편집입니다. 기존 속성을 삭제하거나 scope를 바꾸는 편집, Source 삭제·재생성은 지원하지 않습니다. MCP Source는 이 편집기에서 상태 변경만 지원합니다.
3. 변경안을 열어 대상·현재 값·요청·유효 기한을 확인하고 별도로 동의해 적용합니다. 비활성화는 그 Source를 참조하는 질의에 영향을 줄 수 있습니다.
4. 서버는 확인한 fingerprint를 적용 직전에 다시 검사합니다. 오래된 변경안은 현재 값을 덮어쓰지 않습니다. 한 앱 인스턴스의 Source 쓰기는 직렬화하지만 외부 클라이언트까지 잠그는 분산 잠금은 아닙니다.
5. 요청한 변경의 DB 재조회와 기록 저장이 모두 확인돼야 성공으로 표시합니다. 오류·시간 초과·부분 DDL은 현재 상태와 이력을 먼저 확인하며 자동으로 반복하지 않습니다.

DB가 반환한 대문자 식별자 인용부호는 편집 시 정규화합니다. 실제 기록에는 DB에서 읽은 값이 남습니다. Credential 이름과 설정은 기록될 수 있으므로 설정에 비밀번호·토큰·키 본문을 넣지 마세요. 지원 속성의 비밀 필드 이름은 입력·보관 전에 거절합니다.

## 기록 읽기

대상 행의 **설정 변경 이력**을 선택하면 최근 30건을 보여 줍니다. 한 기록의 **상세**에서 변경 전후 값을 확인합니다. 새로고침은 대상 필터를 해제합니다. 기록은 DB에 남아 재로그인 후에도 조회할 수 있으며, 이 화면은 이력을 삭제하거나 과거 상태를 자동 복원하지 않습니다.

| 표시 | 의미 |
| --- | --- |
| 변경·재조회 확인 | native 호출, 요청 값의 DB 재조회, 후속 기록 보관이 확인됨 |
| 현재 DB 상태 확인 필요 | native 오류 또는 재조회 불일치·실패가 있어 실제 상태를 확인해야 함 |
| 변경 전 보관됨·후속 확인 필요 | 변경 전 기록은 커밋됐으나 완료 기록을 확인하지 못함. 변경 실패로 단정하지 않음 |

## 생성 콜백 설치 기록

사전 API 패키지 body v4는 긴 한국어 등록 표현에 조사가 붙을 때의 검색을 보완한다. UI 사전 검색과 설치용 API에서 공통 SQL을 사용한다. 기존 배포 v2·v3의 정확한 소스만 업그레이드 대상으로 인식하며 사용자 수정본을 덮어쓰지 않는다. 전역 콜백의 원 질문 복원 버전 v6와 사전 API body v4는 서로 다른 구성 요소다. 새 ADB에서 v3→v4 전후 긴 표현 정의 0→1건과 설치·업그레이드 이력 2건을 확인했다. [새 환경 검증 범위](fresh-environment-rehearsal.md)를 참고한다.

**업무 용어 검색 함수**의 이력에는 구성 요소 이름, 식별된 버전, 실제 소스 SHA-256, 모듈 상태와 설치 결과를 보관합니다. 함수 원문은 기록에 복사하지 않습니다. 코드 원문과 차이는 Git에서 관리합니다. 설치 전에 전후 기록용 저장소가 준비돼 있어야 합니다. 기존 생성기의 알려진 구버전만 업데이트하며 알 수 없는 함수를 덮어쓰지 않습니다.

프로필 `semantic_source` 연결 편집 이력과 업무 용어 개정 이력은 기존 화면에서 계속 확인합니다. 이 기능은 DB Companion을 통해 수행한 Source 설정·생성 콜백 설치부터 기록합니다. 외부 SQL 클라이언트의 변경, 이전 변경, 모든 객체 DDL을 소급 수집하는 DB 감사 기능은 아닙니다. AI 질문·실행 결과의 보관과도 범위가 다릅니다.

실습 검증에서는 새 일반 계정에서 저장소 미준비 차단, Source 생성·속성·상태 변경, 오래된 변경안 거절, 다른 소유자 조회 거절, 재로그인 조회와 알려진 콜백 v3→v4의 설치 메타데이터를 확인했습니다. 이는 모든 Oracle 버전·인증 경로의 호환성 보장을 뜻하지 않습니다.

### 첨부 문맥을 다시 검색하는 오류

전역 콜백 v6는 UI의 `BUSINESS DICTIONARY JSON`, 사용자용 AI 함수의 `REFERENCE JSON`, Oracle SQL 수정 요청에서 원 질문을 먼저 복원합니다. 첨부된 정의와 SQL을 다시 업무 용어로 검색하면 원래 질문이 짧아도 `ORA-20061: Token limit exceeded`가 발생할 수 있습니다. 모델 출력 토큰 수를 늘리는 것으로 해결되지 않습니다.

정리는 최대8단계이며 단계마다 입력이 짧아져야 합니다. 입력 문맥은64,000자, 복원된 질문은8,000자까지 허용하고, 잘못된 JSON·과도한 중첩은 명시적으로 거절합니다. 끝이 완성되지 않은 표식이나 뒤에 다른 사용자 문장이 있는 입력은 임의로 잘라내지 않습니다. 모델에 전달하는 근거는 유지하며 콜백의 검색 입력만 원 질문으로 제한합니다.

이미 첨부된 질문이 본문에도 반복되면 마지막의 완전한 영역을 먼저 해석합니다. 앞쪽의 내부 표식과 마지막 JSON을 섞어 파싱하지 않습니다. 기존 앱 생성 v4·v5 소스와 정확히 일치할 때만 `LEGACY`로 인식해 미리보기 후 v6 콜백을 교체합니다. 사전 API·검색 함수·사용자가 수정한 코드는 덮어쓰지 않습니다. 설치 이력에서 전후 콜백 버전·해시·성공 상태를 확인할 수 있습니다.

2026-11-26 격리 합성 데이터 실습에서 실제 Oracle 입력 복원13건, 실제 사전 결과 비교5건을 통과했습니다. DB Companion으로 v5→v6를 적용하고 재로그인 후 전후 버전·해시·`SUCCEEDED`를 확인했습니다. 사용자용 `ASK`의 첨부 문맥을 네이티브 Semantic Source에 전달한 SQL 생성·실행에서 지역별 AU3/2/1이 기대값과 일치했습니다. 이는 소유자 경로의 결과이며 DDS 사용자의 네이티브 호출에서 별도로 관찰한 `ORA-01435`/`ORA-16963`까지 해결했다는 의미는 아닙니다.
