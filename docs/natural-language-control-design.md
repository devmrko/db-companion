# 자연어로 교육 환경을 구성하고 검증하기

상태: 전체 확장은 설계안. 현재 구현은 `AiSetupAssistantService`의 대화 저장·코멘트·제약조건 활성화 3종과 선택형 조회 Tool 호출이다. [선택형 서비스 Tool 사용 방법](service-tools.md). 아래 전체 작업 실행기가 이미 구현됐다는 의미가 아니다.

## 사용자가 할 일

사용자는 메뉴별 설정 대신 목표를 요청한다. 예: “업무 용어를 연결해 사업 AU를 조회하고, EU/APAC 사용자별 결과와 변경 이력까지 확인해 줘.” 도우미는 관찰한 상태에 맞는 작업을 순서대로 제시하고, 필요한 값만 묻고, 적용 결과를 실제 DB에서 확인한다. 수동 화면과 SQL 사용방법도 같은 작업에 연결한다.

## 하나의 작업을 공유

기존 `setup/capabilities.json`, `AiSetupCatalog`, 기능별 미리보기·적용·이력 서비스를 재사용한다. 화면용 변경 로직과 자연어용 변경 로직을 따로 만들지 않는다. 모델은 작업 ID와 형식이 정해진 입력만 제안하고, 서버가 현재 상태·소유자·권한·버전·지원 API를 다시 확인한다. 모델이 생성한 임의 SQL을 실행하는 인터페이스는 추가하지 않는다.

각 작업의 계약은 다음 정보를 가진다.

| 정보 | 의미 |
|---|---|
| 작업 ID·입력 형식 | 프로필 생성/속성 변경, 용어 개정, Source 연결 등 실제 지원 작업 |
| 실행 주체 | 일반 소유자, DB ADMIN, OCI 관리자, APEX 개발자 |
| 선행 조건·조회 | 필요한 저장소·권한·객체와 현재 확인 결과. 조회 실패는 미확인 |
| 미리보기 | 실제 대상·변경 전후·SQL/API·외부 전송과 비용 |
| 적용 | 기존 기능 서비스에 위임. 미리보기 버전·소유자·유효기간 재확인 |
| 결과 확인 | 실제 DB 값, 변경 이력, 대표 질문·기대 결과 |
| 복구 | 재조회·수정 경로. 실패 후 DDL 전체 자동 재실행 없음 |

계획의 단계별 상태는 미시작·미리보기·사용자 확인 대기·실행 중·재조회 확인·실패·결과 미확인·외부 담당자 작업 필요를 구분한다. HTTP200, 모델의 “완료” 문장, 이력 저장만으로 실제 성공을 판정하지 않는다. 작업 계획과 실행 결과는 기존 앱 기록 구조에 별도 유형으로 보관하고 단계/요청 ID로 연결한다.

## 교육 흐름과 기존 실행 경로

| 사용자 요청 | 재사용할 경로 | 확인 기준 |
|---|---|---|
| 가상 데이터 준비 | `DemoDataPrompt`와 사용자가 검토할 파일·SQL 실행 경로 | 테이블·행 수·독립 기대값 |
| 계정·권한 준비 | `AccountSetupService`와 기능별 권한 미리보기 | 대상 계정 재로그인 후 실제 기능 조회 |
| 코멘트·업무 정의 변경 | 메타데이터 편집·업무 용어 개정 서비스 | 실제 값·전후 이력·검색 결과 |
| 검색·콜백 준비 | 사전/Oracle Text 설치와 인식된 코드 설치기 | 컴파일·버전·해시·원 질문/첨부 검색 비교 |
| Source·프로필 구성 | `SemanticContext` 관련 서비스·`ProfileEditService`·`AiCreationService` | 실제 설정·이력·SQL 생성 |
| 이력 준비 | 기존 설치·수집·대상별 조회 위임 서비스 | 일반 계정의 기록·재로그인 조회 |
| 사용자별 접근 | 기존 DDS 사용자·역할·Data Grant 서비스 | 같은 SQL의 실제 신원·허용/제외 행 |
| 자연어 조회·Agent | 기존 Select AI 요청·실행·Agent Tool 경로 | 원 질문·사용 근거·실제 Tool/SQL·기대 결과 |

모든 행을 모델 설명만 추가해 지원 완료로 표시하지 않는다. 작업별 기존 서비스 어댑터·미리보기·실제 적용·재검증이 구현된 경우에만 실행 가능으로 노출한다. 현재 등록되지 않은 작업은 미지원/담당자 작업으로 표시한다.

## 처음부터 구성할 때

대상 프로필과 도우미가 사용할 모델 설정을 구분한다. 대상 프로필이 아직 없어도 기본 진단과 최초 준비 경로를 볼 수 있어야 한다. 도우미 실행용 모델도 없다면 카탈로그 기반 준비 안내부터 제공하고, 모델이 준비된 뒤 자연어 계획 생성을 사용한다. 별도 외부 모델 또는 MCP 클라이언트 모델을 이용하는 연결은 명시적으로 구성된 경우만 제공하며, 현재 지원된 것으로 가정하지 않는다.

ADMIN 단계는 기존 소유자 세션에 관리자 권한을 붙여 실행하지 않는다. 담당자가 적절한 계정으로 로그인해 같은 계획의 담당 단계를 확인/적용하고, 원래 사용자 세션에서 재진단한다. OCI 도메인·정책·ADB ACL·APEX 앱 Import는 별도 API/도구와 실행 신원이 필요하다. 연결된 도구가 없으면 필요한 변수·CLI/SQL·완료 확인을 제공하고 외부 단계 대기로 남긴다. 비밀값은 모델 입력·계획·이력에서 제외한다.

## 확인과 재개

처음에는 단계별 변경안을 확인하고 실행한다. 동일 주체·범위의 여러 단계를 한 번에 승인하는 방식은 계획 전체와 적용 전 상태를 검토할 수 있을 때만 지원한다. 대상·입력·프로필 버전·선행 조건이 바뀌면 승인을 무효화한다. 의존 단계 실패 시 후속 단계를 중단하고, 성공한 단계는 실제 상태를 재조회해 유지한다. 응답이 없는 AI/DDL 요청을 중복 실행하지 않는다.

“설명만”, “변경하지 마”, “취소”, “이 단계까지만”, 다른 대상/스키마 요청과 이전 토큰 재사용을 검증한다. 자유로운 설명 텍스트와 실행 가능한 작업은 분리한다. 기존 기능의 SQL?·전체 코드·미리보기는 자연어 화면에서도 같은 원본을 제공한다.

## Java 실행 관리자와 DB 모델 인터페이스

사용자가 제안한 구성은 Java에서 계획·Tool·승인·상태를 관리하고 LLM 호출만 DB 인터페이스로 제공하는 방식이다. 기존 `AiAssistantRepository.generate()`의 JDBC·Select AI 프로필 호출을 모델 어댑터 내부에서 재사용한다. 모델 연결과 실제 설정 변경을 분리하고, 자연어 화면과 기존 화면은 같은 기능 서비스를 호출한다.

`UI → Java 실행 관리자 → 모델 어댑터 → JDBC / DBMS_CLOUD_AI.GENERATE → 작업 제안 → Java Tool 실행기 → 기존 서비스 → DB 재조회`

도우미가 사용할 모델 프로필과 변경 대상 프로필은 독립적으로 선택한다. 모델 요청의 옵션·전송 범위·호출 수와 실행 주체를 기록한다. 업무 질의용 Semantic Source를 설정 제어 요청에 자동으로 덧붙이지 않는다. 기존 프로필·Credential·OCI IAM을 재사용하되 DB 모델 인터페이스가 어느 호출 기능을 실제 제공하는지 확인한다.

Spring AI 또는 LangChain4j를 도입한다면 해당 모델 인터페이스의 어댑터를 구현한다. DB의 텍스트 응답을 프레임워크의 메시지·작업 요청으로 변환하는 부분과 필요한 Tool 명세 전달을 검증해야 한다. Native Tool Calling·스트리밍·토큰 사용량을 DB 호출이 제공하지 않으면 지원된 것으로 표시하지 않는다. 정해진 JSON 작업 형식을 사용할 때도 엄격한 파싱과 서버의 작업/입력 검증을 유지한다.

권한·소유자·SQL 미리보기·버전 확인·변경 이력·실제 성공 판정은 DB Companion 서비스의 책임이다. 프레임워크의 자동 Tool 실행이나 재시도가 이를 우회하지 않도록 한다. DB 변경은 기본적으로 직렬 실행하며, 세션/로그인 신원을 모델이 정하거나 ThreadLocal DB 연결이 임의의 비동기 작업으로 전파된다고 가정하지 않는다. 영속 계획은 DB 연결 자체를 저장하지 않고 단계 ID·대상·검증 가능한 상태와 실행 결과를 저장한다.

프레임워크 선택은 작은 호환성 검증 후 확정한다. Java/Spring의 모델·Tool 연결은 Spring AI 또는 LangChain4j가 후보이며, 여러 담당자·오랜 승인 대기·재시작 후 재개 등 실행 흐름의 요구가 커질 때 LangGraph 같은 별도 실행 계층도 비교한다. 현재 설계가 해당 라이브러리 도입·호환성 검증까지 완료했다는 뜻은 아니다.

참고: [Spring AI Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html), [LangChain4j Tools](https://docs.langchain4j.dev/tutorials/tools/), [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview). 2026-11-26 공식 문서 확인. 모델 요청/Tool의 표준 연결과 장기 실행 상태 관리의 역할을 비교하는 근거이며, DB 어댑터의 실제 호환성을 증명하지는 않는다.

## 인스트럭션과 서비스 호출 프로토콜

현재 선택형 구현은 `AiSetupToolLoop`에서 빈 인자의 조회 Tool 3종을 제공한다. 모델은 `type=tool_call`과 등록 이름·빈 `arguments`를 반환하고, Java가 기존 진단/조회 서비스를 호출한다. `type=final`의 설명과 단일 변경 후보는 기존 미리보기·적용 흐름으로 이어진다. 모델 최대 4회, Tool별 1회 한도를 적용하며 기본 단일 분석 경로는 유지한다. 아래 변경 Tool 프로토콜은 이후 확장 예시다.

DB 모델 호출이 Native Tool Calling을 제공하지 않아도 인스트럭션에 등록된 작업의 이름·설명·입력 JSON 형식을 넣고, 응답을 정형 작업 제안으로 받을 수 있다. 아래는 확장할 프로토콜 예시이며 현재 제품 API가 아니다.

```json
{"type":"tool_call","id":"step-1","name":"profile.previewAttributeChange","arguments":{"profile":"AU_PROFILE","attribute":"comments","value":true}}
```

Java 실행기는 이름을 등록된 핸들러로 해석하고 입력 형식을 검증한다. 핸들러는 기존 `ProfileEditService.edit/save` 같은 서비스를 호출한다. 클래스명·메서드명을 모델이 임의로 정해 리플렉션으로 실행하지 않는다. 로그인 신원과 대상 소유자는 인증된 서버 컨텍스트로 결정하고 모델 입력으로 대체하지 않는다.

Tool 결과에는 호출 ID·실제 대상·현재 상태·변경 전후·미리보기 토큰의 서버 측 참조·검증 결과·이력 참조를 둔다. 변경 승인은 모델의 `approved:true`가 아니라 실제 사용자가 검토한 계획/단계와 서버에 보관된 토큰·버전에 결부한다. 모델에는 필요한 결과만 전달하고, 최종 답변도 검증된 결과 ID를 근거로 구성한다. Tool 조회 성공·DB 변경 성공·모델의 최종 설명 성공은 별도 상태다.

인스트럭션은 지원 작업 선택, 부족한 입력 질문, 미리보기 우선, 변경 사실을 추측하지 않기, 실패/결과 미확인 시 중단을 정의한다. 실제 권한·입력·중복 실행·상태 검사는 Java에서 수행한다. 중복 키·추가 JSON·미등록 작업·지원되지 않는 속성은 서비스 호출 전에 거절한다. 향후 프레임워크 도입 시에도 같은 핸들러와 결과 계약을 재사용한다.

## 완료 기준

새 일반 계정에서 데이터 준비→정의/검색→Source/프로필→이력→자연어 질문/실제 조회→DDS 결과 대조를 재현한다. 자연어 설명·계획·미리보기·적용·검증 기록을 각각 확인한다. 기존 교육 환경을 변경하지 않는 별도 합성 계정과 독립 기대값을 사용한다. 종료한 DDS 네이티브 직접 생성의 원인 조사는 이 확장 설계의 범위가 아니다.
