SQL? 구현 참고 / Implementation reference

이 문서는 DB Companion 자체 저장소·처리 절차의 설명입니다. Oracle 공식 API 문서와 구분합니다. SQL?는 예제를 표시·복사할 뿐 실행하지 않습니다.

This guide describes application-owned stores and workflows, not Oracle dictionary APIs. SQL? displays and copies examples; it does not execute them.

메타데이터 이력 · AI 설정 이력 · 앱 기록 · 온톨로지 · 관계 분석 · 결과 검토

메타데이터 이력 / Metadata history

DBC_METADATA_HISTORY는 대상 스키마의 코멘트·Annotation 변경 기록입니다. 직접 SELECT 권한과 객체별 위임 이력 권한은 다릅니다. 위임 사용자는 설치 계정의 DBC_METADATA_ACCESS.inspect(schema, object) 및 entries(schema, object, page)를 호출합니다. SESSION_USER를 검사하며 페이지는 1부터 시작합니다.

패키지 EXECUTE만으로 모든 객체의 이력을 볼 수 없습니다. 대상 등록·코드 상태와 별도 조회/관리 규칙도 검사합니다. 관리 권한은 기존 수집기의 ON/OFF 권한이며 새 트리거 설치나 업무 데이터 권한이 아닙니다. 사용자별 허용·제외는 이력 접근 범위이지 변경 기록 수집 대상 필터가 아닙니다.

Direct table access differs from delegated access through the installer's fixed package. Every call checks SESSION_USER and object-scoped rules. Page 1 returns ten rows plus one lookahead. Delegated management toggles existing collectors; it cannot install triggers or grant business-data access. Access rules do not exclude changers from collection.

구현: HistoryAccessRepository.java, MetadataHistoryRepository.java, db/history/access-body.sql. 권한·위임 상세 설계 / Access design

AI 설정 변경 이력 / AI configuration history

DBC_AI_HISTORY는 설치된 앱 이력 저장소입니다. 객체 종류·이름, 변경자, 전후 JSON 및 결과를 기록합니다. 앱 밖의 모든 변경을 수집한 Oracle 감사 원본이나 AI 실행 전수 기록으로 해석하지 마세요.

DBC_AI_HISTORY stores captured configuration changes, before/after JSON, actors and outcomes. It is not the Oracle audit trail or an exhaustive record of external changes or AI executions. Source: AiHistorySql.java.

선택 저장·실행 기록 / Application records

DBC_APP_RECORD는 로그인 소유 스키마의 앱 저장소입니다. RECORD_TYPE, RECORD_ID, STATE와 JSON PAYLOAD를 함께 해석해야 합니다. 문제 질문은 SELECT_AI_PROBLEM, 선택 저장한 시도는 SELECT_AI_ATTEMPT이며 parentId로 연결합니다. 상태의 의미는 기록 유형별로 다릅니다.

단순 INSERT는 앱의 payload 검증·동시 변경 확인·이력 처리 전체를 대신하지 않습니다. 미저장된 질문·응답이나 과거 실행을 소급 수집하지 않습니다. SQL?의 저장 예제는 처리 단계 설명이며, 앱 화면의 확인된 저장 절차를 권장합니다.

Interpret RECORD_TYPE and STATE together with the payload. Selected problem attempts link to their parent via parentId. A storage INSERT does not reproduce validation, concurrency checks or history capture, and cannot recover unsaved past calls. Sources: AppRecordRepository.java, AppRecordSql.java.

온톨로지 버전·관계 / Ontology revisions and relations

DBC_ONTOLOGY_CATALOG에 원본 메타데이터, 업무 정의, 관계 및 RDF 표현을 포함하는 문서를 새 버전으로 저장합니다. 최신 버전과 승인 상태는 별개입니다. 과거 승인본이 있더라도 최신 초안이 자동으로 승인되지는 않습니다. SQL?의 JSON 조회는 저장 문서 확인이며 실시간 업무 데이터 JOIN이나 SPARQL 실행과 다릅니다.

DBC_GLOSSARY_TERM 검색 예제는 온톨로지 승인 정의의 검색 투영입니다. 독립 업무 용어 사전 DBC_BUSINESS_TERM과 같은 저장소가 아닙니다. 선택한 관계로 업무 행을 조회하는 JOIN 예제는 실제 키·필터·권한을 따로 확인해야 합니다.

Ontology documents are versioned in DBC_ONTOLOGY_CATALOG. Latest and approved are distinct. JSON inspection does not run a business-data join or SPARQL. DBC_GLOSSARY_TERM is the ontology search projection, not the independent DBC_BUSINESS_TERM dictionary. Manual join examples require verified mappings, filters and permissions. Sources: OntologyRepository.java, OntologyQueryRepository.java.

관계 분석 계획·후보 저장 / Discovery plans and candidates

ONTOLOGY_DISCOVERY_PLAN과 ONTOLOGY_DISCOVERY_CALL은 DBC_APP_RECORD의 기록 유형입니다. 계획의 SUCCEEDED는 계획 저장 성공입니다. 호출 기록은 runId로 연결하고 STATE, stage, issues를 별도로 확인합니다. 저장된 index는 0부터, 화면의 호출 번호는 1부터입니다.

정상 후보는 온톨로지 버전의 links와 RDF에 CANDIDATE로 저장합니다. 후보 저장은 승인과 다릅니다. 실패·응답 불명 호출은 자동 재시도하지 않고, 저장 실패나 정의 변경은 진행을 중단합니다. SAVE 복구는 저장만 재시도합니다. 계획을 다시 불러오면 미시도 호출만 검증·동의 후 이어갑니다. 분석 완료도 실제 업무 관계를 모두 발견했다는 보장은 아닙니다.

Plan persistence is not analysis completion. Inspect per-call receipts separately. Valid mappings become CANDIDATE ontology links/RDF, not approved relations. Unknown/failed calls are not automatically retried; storage failures or changed definitions stop processing. SAVE recovery does not call AI. Resume unattempted calls after checks and consent; complete plan coverage does not guarantee exhaustive business relationships.

구현: OntologyDiscoveryRepository.java, OntologyDiscoveryArchive.java. 저장·복구 상세 / Storage and recovery design

결과 설명·AI 검토 / Executed-result review

성공한 실행의 resultId·SQL 해시·시각을 확인하고 당시 질문, SQL, 용어·온톨로지 근거, 확정 조건, 결과 요약 및 선택 비교 기준을 전송합니다. 결과 셀 값은 제외합니다. 다만 SQL 리터럴이나 직접 입력한 비교 기준에 민감한 값이 있을 수 있어 전송 전 검토가 필요합니다.

검토 프로필로 DBMS_CLOUD_AI.GENERATE(action => 'chat', attributes => '{"conversation":false}')를 1회 호출합니다. SQL 재실행·자동 재시도는 하지 않습니다. SQL? 예제는 완성된 프롬프트 CLOB을 바인드하는 호출부만 보여 줍니다. 스냅샷 검증과 프롬프트 조립은 앱 처리입니다. AI 의견은 수치의 정답이나 VPD/마스킹 적용 증빙이 아닙니다.

Review binds to a successful execution snapshot and sends SQL, captured definitions, confirmed conditions and summary counts, never result cell values. SQL literals and user baselines still require privacy review. One stateless chat call uses the review profile. There is no SQL rerun or automatic retry, and the opinion cannot prove numeric correctness or security enforcement. Source: SelectAiResultReview.java, SelectAiTestService.java.
